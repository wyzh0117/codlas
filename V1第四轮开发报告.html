一、本轮范围：这一条门为什么值得两侧同时写

V1-D 记了三轮 ◐，缺的从来不是读文件的那一半——Manual Import、transcript、CLI session、git log 都有适配器了。缺的是 §34 与 §35 那一行：活的网页会话如何进入工作台，以及工作台编译好的 Context Pack 如何回到网页。 §38.5 的 MCP 那扇门（ADR-026 / ADR-028）读得出去、读不进来，替不了这条链路。

本轮按用户留下的三句话推进：①按"还欠着"记——写回时 V1-D 仍是 ◐，只是欠的东西换了名字； ②把"立刻收尾"和"接着做"的部分都完成——宿主 + 扩展 + §58 E2E 那一行 + 上一轮 README 里那份与实现对不上的安装说明； ③检查整个 V1 是否全部完成——见第八节的逐段清点。

为什么必须两侧对着写：通道一头是 Rust 宿主、另一头是 JS 扩展，中间只有 JSON。 任何一侧单方面定义字段名，缺陷都会等到下一个人第一次真跑时才现形。本轮抓出的两处（第四节）就是这么找出来的。

二、宿主这一侧：native_messaging.rs 与 wp host

四个动词、一问一答、永不监听。没有端口、没有 socket、没有后台守护——通道的生命周期就是 Chrome 给的那个 stdio。

commandpayload回答（data）落点
hello{} protocol / commands / capabilities / allowedOrigins / project / autoExecute:false 只答策略，不碰库
capturesource / conversationId / title / messages[] action:"captured" + messages{inserted,duplicate} + events{appended,pending,candidate} + nearDuplicates + project IngestPipeline::ingest_messages
openurl action:"openTab", url 指令；由 service worker 执行
injecttext action:"fillComposer", text, send:false, note 指令；§7.8 写在协议里
  • 帧：四个小端字节长度前缀 + UTF-8 JSON。声明超过 1 MiB 的帧在解析任何 JSON 之前被拒—— 这是 §35 的 size 唯一说得通的位置；恶意或写坏的扩展无法用四个头字节让工作台分配 4 GiB。
  • 五个检查各有一个拒绝前缀：origin rejected / command rejected / payload rejected / size rejected / project scope rejected。测试按前缀断言，所以一个检查失效不会被另一个的失败掩盖。
  • 一条坏帧只结束那一帧：会话继续（§62——静默才是失败，报出来的不是）。
  • 不是第八个适配器：浏览器推来的线程走 ingest_messages。适配器是读者， 活的会话在浏览器那一侧是被推的一方；给它造一个"主动读"的 trait 只会把"谁来发起"说假。
  • wp host 是子命令，不是第十三个成员：§60 的 12 份 manifest 巡检因此不必改写。 manifest 写两个文件——Chrome 的记录 + 记录所指向的 wrapper 脚本，因为 Chrome 不传参数， --db 与 --project 只能烘焙进脚本，路径逐单引号转义。
  • stdout 属于协议：serve 期间人类可读的那一行走 stderr，这是全 CLI 唯一一处这样的命令。

三、扩展这一侧：apps/extension/（MV3，零依赖、零构建）

文件职责守的条款
manifest.jsonMV3；权限只有 nativeMessaging / activeTab / scripting / storage；无远程代码、无内联脚本§34 的"不负责"清单
background.jsservice worker：§35 前置校验 + 唯一入站门（只收弹窗消息）+ 执行宿主给的 openTab / fillComposer§35、§7.8
content.js读页面（三套站点选择器 + generic 兜底，读不出角色就跳过并报数）、写输入框（只 input/change）禁止 9、§7.8
popup.html/js五个按钮 + 状态区逐字显示宿主的拒绝句子；全程 textContent§62 Degradation
  • 校验在 native messaging 之前：协议版本、origin 白名单、已知 command、payload 形状 （未知字段拒绝、role 只认 user/assistant、at 不是 RFC3339 就拒绝而不是猜）、project 字段形状、 序列化后 245760 字节硬上限。宿主自己也有同样一份。
  • generic web 的"用户授权"就是那次点击：弹窗按钮签发一次性同意凭据（60 秒、用过即废、只在 worker 内存， worker 一睡就没）。content script 从不自己发起请求，页面也够不着 chrome.runtime.onMessage（没开 externally_connectable），所以每条请求都能追回到一个人按过的键。
  • 填而不发：不派发 Enter、不 requestSubmit()、不点发送键；宿主即使回 send:true 也照 §7.8 忽略并在状态行说明。输入框已有草稿时追加而不是覆盖。
  • 不联网、不建库：代码里没有 fetch / XMLHttpRequest；扩展不判断项目状态（禁止 9）， 聊天记录只是证据，最终记忆由 Rust 核心折叠出来。

四、两边对接时抓出的两处（都已就地修订进 ADR-031）

问题原先现在
§35 的 origin 检查有两副面孔 扩展用自造 scheme codlas-extension://popup 报 hello / open， 而宿主只接受 https://<host>——自检与"打开目标网页"永远 origin rejected。 不经手页面材料的 hello / open 接受扩展自己的 chrome-extension://<id> （那枚 id 正是 Chrome 按 allowed_origins 已核过的东西）；capture / inject 仍必须报页面 origin。 open 的目标 URL 另有它自己的白名单，两件事不互相顶替。
capture 的成功答复被当成未知动作 applyHostAction 的兜底分支给 {action:"captured"} 写一句"只认 openTab 与 fillComposer，已忽略"—— 正常路径上的一句假话。 captured 是结果不是指令，直接返回；兜底只报真正不认识的动作。
同轮改写的那份 README：apps/extension/README.md 原先描述的是"wp host manifest 打印一份 json，你原样粘贴"， 而实际命令是写两个文件并打印 mkdir / cp 两行；协议表也缺 capture 的回复形状与 origin 的两副面孔。 ADR-031 明写了这条维护费：JS 改了字段名，Rust 只会以 payload rejected 回答，所以两份必须同轮动。

六、§58 的 E2E 那一行第一次真跑通，§53 顺路被看见一次

cli_e2e 第 20 条 a_browser_session_round_trips_through_the_native_host 用自己重写的一份编解码 驱动真 wp host serve——不复用 crate 的 codec，因为共享 helper 会替宿主隐瞒它自己发出去的字节。 链路：Browser → Extension → Native → Event → State → Project Map → Select Issue → Context Pack → Browser Prepare。

  • 同一轮撞上 §53：这个 fixture 项目 allowCloudModel=false，所以 context build --to chatgpt 的包被整包拒绝， 测试把这句拒绝当成本轮的一个断言，链路上用的是"不声明去处"的那份包。这不是绕行：§53 管的正是"去处"， 而把包搬进浏览器的人是 §7.8 里那个动手的人。
  • 最后一帧之后又送一帧坏 origin：拒答之后 state show 的 Issue 数没变——通道的失败不改变项目事实（禁止 4）。

一、ADR 是什么，为什么需要它

ADR = Architecture Decision Record，架构决策记录。一条 ADR 只回答一个问题： 为什么代码今天长这样。它不是设计文档的复述，也不是待办清单，而是一段已经发生、 并且希望后来者不要重新争论的决定。本项目里每条 ADR 固定四块：

  • Context — 决定被迫出现时的约束（哪份文档、哪个缺陷、哪个禁止项在背后推它）。
  • Decision — 现在为真的那件事，写到端口名、表名、函数名的精度。
  • Consequences — 这个决定让人以后不能做什么，以及代价是什么。
  • Ref — 指向 V1_DEVELOPMENT.md / PROJECT_MASTER.md 的条款号，或指向它修订、 实现的另一条 ADR。

编号是不可回收的：ADR-003、005、006、007、008、009、010、012 没有独立条目， 因为 PROJECT_MASTER §7 / §19 已经把那些决定钉得够死，另开一份文件只是复述总控；往后从 ADR-031 继续往下排，缺号不是遗漏。反过来，前瞻性的架构意图不属于 ADR，属于 docs/evolution/ 下的 AEP（Architecture Evolution Proposal）—— AEP 说"什么时候该改"，ADR 说"当初为什么这么定"。

三、写 ADR 的规则（从 PROJECT_MASTER §23 / §24 与 V1_DEVELOPMENT §57 收拢）

  • 只有已经在代码里为真的决定才进这里；还在计划的写进 docs/evolution/ 当 AEP。
  • 决定被后续轮次改变时就地修订并在 Status 标 amended 日期（改了什么）， 不叠第二份说法——同一件事有两份记录，就等于没人知道哪份为真。
  • 一条 ADR 只记一个决定。缺陷驱动的决定（如 ADR-014、ADR-018、ADR-024）必须写清 原实现为什么错，而不只是写"修好了"。
  • 新增重大功能却不说明它与原始目标的关系（禁止 10），这条 ADR 就是不合格的回写材料。
  • 本页是容器不是来源：正文文字逐条来自原 ADR-0NN-*.md，未作改写； 将来新增 ADR 直接在页内追加一节，并同步 docs/adr/README.md 的指针。

ADR-001 — Local-first storage

Statusaccepted (design), implemented 2026-10-03
RefPROJECT_MASTER §7.1, V1_DEVELOPMENT §4.1

Context

The product exists so a single developer keeps a project's design history. That history is the most valuable asset the tool holds, and it must survive losing network, losing an agent account, or closing the laptop.

Decision

Every record — project, charter versions, scope versions, architecture baselines, sources, conversations, messages, events, entities, evidence, snapshots, context packs, audit rows — lives in a local SQLite file. Nothing is uploaded, mirrored or backed up to a service as part of V1. Cloud appears only as AEP-001, whose trigger conditions are unchanged.

Consequences of the choice that show up in code:

  • SqliteStore::open(path) is the only place a path is resolved; the default data dir is chosen by the caller (apps/cli today), never by a crate.
  • PRAGMA journal_mode = WAL so the workbench can read while an adapter is appending.
  • The .projectpack export (§55) is the only supported way to move a project today.

Consequences

Works offline, no account, no cost. Single-device only until AEP-001 triggers; a lost disk without an export loses the project, which is why export is in V1 scope rather than later.

ADR-002 — Event-first, with a disposable projection

Statusaccepted (design), implemented 2026-10-03
RefPROJECT_MASTER §7.2, 禁止 4 / 禁止 6, V1_DEVELOPMENT §15–§18

Context

A model summary is allowed to observe a project; it is not allowed to be the project's memory. If summaries could overwrite state, one bad rewrite would silently delete history, and nobody could answer "why is the project like this?" afterwards.

Decision

Source → Event → Reducer → Project State is the only write path.

  • Events are append-only, carry actorType, confidence, status and evidenceRefs, and their type must come from vibe_domain::event_catalog (40 §16 constants). Appending an unknown type is a validation error, not a silent accept.
  • Only Accepted events reduce. A candidate below the inbox floor is stored for audit but changes nothing.
  • projector::fold is a pure function: it never reads the entity, artifact or evidence rows it is about to write. Materialized rows are a cache, and dropping every one of them then re-folding must reproduce the same state_hash.
  • There is exactly one ProjectState type; no crate keeps a second copy of project facts.

Consequences

Reading is a join-free cache hit, and time-travel, replay and golden tests are all the same operation. The cost: an event that turns out to be wrong is never edited — it is superseded by another event, so the log grows monotonically and rules must be written to tolerate that.

ADR-004 — Repository ports, and what sits on each side of them

Statusaccepted (design), implemented 2026-10-03
RefPROJECT_MASTER §7.5, V1_DEVELOPMENT §6

Context

The documented risk is the core silently fusing to SQLite, and then a future personal-sync layer requiring a rewrite. The docs already forbade it; the question was what actually enforces it.

Decision

vibe-core::ports declares ten traits and is the only boundary between logic and a store. Eight are the ones named in §6 (ProjectRepository, EventRepository, EntityRepository, ConversationRepository, ArtifactRepository, SnapshotRepository, SearchIndex, SettingsRepository); two more were added because the §49 tables deserved their own contract rather than being smuggled through another port: EvidenceRepository and AuditRepository.

  • vibe-core and every crate above it (state-engine, guard-engine, context-engine, ingestion, search) depend on the traits only. rusqlite is a dependency of exactly one manifest besides the workspace root — crates/storage/Cargo.toml — and appears in source only under crates/storage/src. The other mentions of the word in the tree are the ports' own prohibition comment and the fixture text the architecture-drift rule scans.
  • Repositories bundles the ten as Arc<dyn …> so a use-case service takes one argument and stays &self-callable.
  • EntityStore is a blanket extension trait over EntityRepository so callers get typed entities_of::<Task>() / put_entity() instead of hand-decoding JSON. It must be in scope at the call site — an intentional speed bump that keeps the raw JSON port visible.
  • SqliteStore implements all ten over one Mutex<Connection> and hands them out via repositories(); tests use open_in_memory().

Consequences

A sync engine (AEP-001) can be inserted under these traits without touching a service. The cost is indirection in tests and the discipline to never reach for SqliteStore from a service; the -p build graph makes that violation a compile error rather than a review comment.

ADR-011 — PROJECT_MAP is compiled, and empty sections announce themselves

Statusaccepted (design), implemented 2026-10-03
RefPROJECT_MASTER §10, 禁止 6, V1_DEVELOPMENT §30, §31, §33

Context

§30 forbids letting an LLM rewrite the whole map each time. §10 defines the map as a "readable projection" of current state. The open implementation question was what a deterministic compiler does when a section has nothing to say — dropping the heading is the easiest thing, and also the most dangerous, because a workbench that quietly omits "Active Decisions" is indistinguishable from one that has none.

Decision

  • ProjectMapCompiler::render reads a ProjectState and nothing else — no repository, no clock, no model. compile() supplies the state and the tail of the event log; generatedAt lives on ProjectMap, never inside the markdown body, so identical state produces byte-identical markdown.
  • All thirteen §31 headings are always emitted in the documented order. An empty section renders EMPTY_PLACEHOLDER (_none recorded_).
  • "Next Actions" is generated from declared gaps, not from a model's guess: a missing charter, an unverified completion claim, open issues, dormant AEPs.
  • A compiled map carries the source_state_hash it came from, and ProjectMapCompiler::save persists the pair, so the workbench can prove which state a displayed map was compiled from. compile() is side-effect-free apart from refreshing the projection; a snapshot takes its own copy of the map text so a frozen view cannot drift.
  • Snapshots keep their own map copy; the "since last snapshot" view (§33) is a diff of two states, with its own markdown shape, and is the thing a returning user reads first.

Consequences

The map is cacheable and cheap (§59), and a missing section is information rather than an absence. Wording polish by a model remains optional and outside this path — if it is ever added it must produce a separate field, never overwrite the compiled body.

ADR-013 — One `entities` table with a JSON payload, not one table per object

Statusaccepted, amended 2026-10-06 (implementation deviation from V1_DEVELOPMENT §49, allowed by §50; key corrected by migration v3; the §52 L2 key it cited is now ADR-033's)
Date2026-10-03
RefV1_DEVELOPMENT §49 (full table list), §50 (minimum database version); ADR-033

Context

§49 sketches tasks, issues, decisions, artifacts, milestones, change_proposals, architecture_evolution_plans, drift_alerts as separate tables. §50 then permits collapsing them: "Task / Decision / Issue 可先作为 Entity subtype". The V1 field sets for these objects are still moving — §19 alone requires a task to carry an unverifiedClaim that no table column predicted.

Decision

Follow §50. One table:

entities(kind, id, project_id, status, data_json, updated_at, PRIMARY KEY (kind, id))

plus entity_links for relationships and entity_versions for before/after transitions. Typed access goes through EntityStore; the payload is the domain struct's own serde form, so the struct definition is the schema.

The primary key is the pair, not id alone. The first cut of the baseline keyed entities by id and upserted ON CONFLICT(id) without rewriting kind, so two entities of different kinds sharing an id left one row carrying one kind's name and the other kind's body — a confirmed decision whose subject id happened to equal an issue's id silently turned that issue into decision JSON, and the reducer then failed to decode it (or, worse, decoded it). Migration v3 rebuilds the table with a kind-scoped key; it is a forward migration rather than an edit to baseline v1, because §49's own purpose is that a later release can migrate user data instead of discarding it. Nothing referenced entities(id) as a foreign key, so the rebuild needed no other table.

Charter, scope, architecture baseline, events, messages, evidence, snapshots and audit rows keep their own tables, because those are versioned or append-only records with real constraints (§9 UNIQUE(project_id, version), §15 events.seq, and §52's L2 key on messages — which ADR-033 later widened to (conversation_id, role, content_hash) and rebuilt through migration v4).

Consequences

  • Adding a field to a Task is a code change, not a migration. In V1 that is the right trade; by V2 (entity/architecture graph, AEP-005) the JSON payload is what gets migrated.
  • Querying is by kind, project_id, status (idx_entities_project_kind) and full text; anything more selective has to be promoted to a column. AEP-005 is the planned moment.
  • status is duplicated out of the payload so the guard engine and the inbox can filter without decoding every row. The projector keeps them consistent (§25 keeps DriftAlert.status inside the payload too).

ADR-014 — Event identity: store-assigned `seq`, actor and status inside the dedup key

Statusaccepted
Date2026-10-03
RefV1_DEVELOPMENT §15, §18, §27, §51, §52; ADR-002

Context

Two defects found by the Stage C acceptance tests, both about identity.

  1. The reducer's determinism claim rests on a single total order. If a caller could supply seq, a laptop that was offline for a week would hand back sequence numbers that interleave wrongly with the ones already stored, and replay would stop being reproducible.
  2. event_dedup_key(project, type, source, message, subject, payload) did not include who spoke or what the event's judgement status was. So an agent's TASK_COMPLETED_CLAIM arriving as a pending_review candidate and the user's later confirmation of the very same subject and words hashed to the same key. The confirmation was dropped as a duplicate, and the task stayed open forever with a "confirmed" state that never landed. an_agents_claim_stays_a_claim failed on exactly this.

Decision

  • events.seq is INTEGER PRIMARY KEY AUTOINCREMENT, assigned by the store on insert, and the caller's seq is ignored on write. list_accepted(project, after_seq) and fold-then-project_state both order by it. Tests that need a fixed timestamp own occurredAt, never seq.
  • event_dedup_key takes actor_type and status as two extra components. Identity is "this source material, saying this, as this kind of statement" — so re-ingesting the same transcript row is still idempotent, while a candidate and the fact it was later promoted to are two distinguishable rows.
  • Reviewing an event in place (EventStore::review → patch_event) is the normal promotion path and preserves the original row; appending a fresh accepted event for the same subject is also legitimate, and both now coexist.

Consequences

state_hash covers last_seq, so a state fingerprint is tied to the store's ordering, not to a wall clock — which is what makes cross-machine replay (the_same_log_projects_to_the_same_hash_in_two_stores) meaningful. The cost: a truly identical re-ingest that differs only in judged status creates a second row by design, so inbox counts must be read as "statements", not "facts".

ADR-015 — Drift rules are lexical in V1, and they only ever propose

Statusaccepted
Date2026-10-03
RefV1_DEVELOPMENT §26, §29, §8.6 (PROJECT_MASTER); AEP-004

Context

§26 specifies V1 drift detection as "Rules + Structured Comparison + Optional LLM Judge" and §8.6 states a Drift Alert is a prompt that must not block development. The temptation is to reach for a model to decide "does this contradict that decision". The risk of giving in: an unexplainable alert, a per-check API cost, and a rule that silently changes behaviour when the model changes.

Decision

All six V1 rules are deterministic and run in guard-engine with no model in the loop:

rule signal it can actually see
scope_drift task/issue/proposal wording vs outOfScope + forbidden items
decision_conflict high token overlap with an Active decision and a flipped negation or opposition-vocabulary hit
architecture_drift ArchitectureInvariant.detect patterns matched against artifact paths and layer role; scan_source(state, path, text) is the precise textual path
feature_creep new work with no anchor in mustHave, inScope, an open change proposal or an AEP
repeated_redesign redesign_count ≥ 3, or ≥3 supersede/reverse hits on one subject
stale_assumption active decision older than an injected now minus threshold, contradicted by newer events

Supporting rules that are load-bearing, not incidental:

  • Alert ids are content-addressed over (project, type, summary, subject), so check() is idempotent and never piles up duplicates. An alert a user already judged is never resurrected.
  • Every alert carries non-empty baseline_refs (what it was measured against) and evidence_refs (which events/entities triggered it). An alert that cannot cite its baseline is not allowed.
  • The engine never mutates charter, scope or baseline, and never applies a change proposal's delta. Accepting a proposal records status plus CHANGE_PROPOSAL_ACCEPTED; a user applies it. That is 禁止 5 kept at the engine boundary rather than in the UI.
  • Matching is CJK-aware (bigram tokenizer) because the project's own records are Chinese.

Consequences

Known, documented blind spot: a paraphrased contradiction with no shared vocabulary and no negation marker is missed. That is the exact gap AEP-004 (Basic Drift Rules → Intelligent Drift Engine) exists to close, and its trigger condition is unchanged — the rule layer is the floor it will be measured against, not something it has to be rewritten around.

ADR-017 — The system keychain is explicit opt-in; the default secret store is a 0600 file

Statusaccepted (records a deliberate reading of V1_DEVELOPMENT §53)
Date2026-10-03
RefV1_DEVELOPMENT §53, §54; PROJECT_MASTER §19 禁止 8; ADR-016

Context

§53 states two things at once: "API Key、Token 不进 SQLite 明文" and "使用系统 Keychain。 数据库只保存 secret_ref". The first is an invariant no test or automation may break. The second names one implementation. Writing to the OS keychain is machine-global shared state: a test run, a reindex, or any background invocation would either pop a GUI authorization dialog or leave entries the user did not ask for — the same blast-radius reasoning that keeps release actions behind explicit confirmation.

Decision

SecretStore (put / lookup / delete / describe) is a port in crates/security, with two implementations:

  • LocalSecretStore — the default. One <id>.value plus <id>.meta.json per secret in a directory the caller injects (apps/cli names secrets/ beside the database). Files are created create_new + mode 0600 via create_private. The ref is local:<generated id>; the ref is validated against a lowercase/digit whitelist before any path is built, so local:../escape fails without touching the filesystem.
  • KeychainSecretStore — macOS /usr/bin/security add-generic-password -U, value handed over stdin so it never appears in an argument vector; the RFC3339 -C comment carries createdAt; statuses 44/45 mean absent. Its only constructor takes a KeychainConsent, and the only way to obtain one is VIBE_SECURITY_ALLOW_KEYCHAIN=1 in the environment of the process the user started.

wp secret put --keychain without the variable refuses with a message naming the variable and the file-store alternative; wp secret put without the flag never touches the keychain. The database only ever sees secretRef; wp secret list records name/ref/store in project settings, and describe structurally cannot return a value.

The real-keychain round trip is a manual, #[ignore]d test (crates/security/tests/keychain_opt_in.rs):

VIBE_SECURITY_ALLOW_KEYCHAIN=1 cargo test -p vibe-security --test keychain_opt_in -- --ignored

Consequences

  • V1's out-of-the-box posture is weaker at rest than the keychain: a 0600 file, protected by filesystem permissions only. The invariant §53 exists to guarantee — no plaintext in SQLite — holds for both stores, and apps/cli/tests/cli_e2e.rs proves it by reading every byte of the database file and asserting the value is absent while local:<id> is present.
  • Refs are not interchangeable across stores. local: refs are id-keyed (putting the same name twice creates two secrets; the settings index keeps the newest), while keychain: refs are name-keyed and -U makes a second put an upsert on one account. SecretMetadata.store is therefore always shown beside the ref.
  • store_for (apps/cli/src/policy.rs:195) resolves a ref by prefix. A keychain: ref read back without the consent variable currently fails through LocalSecretStore's ref validation ("not a local secret ref") rather than a message naming the variable — it fails closed, but the wording is indirect. Left as is for V1's single-user setting.
  • Non-macOS platforms keep the file store; the keychain wrapper is /usr/bin/security-bound on purpose. A portable hidden-file backend for other platforms would be its own ADR.

ADR-018 — The full-text index stores what a record says, not how it is encoded

Statusaccepted (fixes four defects the CLI round surfaced)
Date2026-10-03
RefV1_DEVELOPMENT §40 (L2), §43; PROJECT_MASTER §19 禁止 4

Context

The first indexer wrote serde_json::to_string(record) into search_index.body. Using the CLI then produced four defects at once:

  • a hit's snippet was a JSON blob ({"evidenceRefs":["evt:…"]…}) that no one can read;
  • a query for a 64-hex hash or an evt: id matched nearly every row, because the encoding contained those strings;
  • L1 hits whose record had no body rendered as blank lines;
  • wp search bypassed §40's L1/L3 layers entirely, so wp reindex was unreachable and the three layers never actually ran together.

Each defect passed the library suite of the day; all four were found by running the binary. That is the instrument ADR-020 exists to keep.

Decision

  1. searchable_text(value) (crates/storage/src/entity.rs) walks the JSON tree, keeps string leaves, and joins them with ". ". is_opaque drops ≥32-char pure-hex strings, so ids and hashes stay L1's business instead of flooding L2. Events index "<type> <searchable_text(payload)>".
  2. SearchService::find_in(project, query, kinds, limit) runs the three §40 layers as one pipeline: L1 catalog::records (structured filters, kind-scoped), L2 FTS5 snippet() over the same scope, L3 entity_links walk in both directions skipping hits whose kind the caller excluded. find is the no-filter delegate.
  3. An L1 hit with an empty body falls back to the title (Record::hit): §40 says a hit must be explainable, and a blank snippet explains nothing.
  4. wp search [--kind …] calls find_in and prints the layer label, score and snippet; wp reindex re-encodes every entity and event through the same searchable_text path.

Consequences

  • A snippet now reads as the sentence the user wrote. The test crates/search/tests/retrieval.rs::a_hit_reads_as_prose_and_its_encoding_matches_nothing pins both halves: the prose appears, and evidenceRefs / createdByEvent / a 64-hex id match nothing.
  • §40's layer label is user-visible (structured / full_text / relation), so a hit can still be explained after ranking changes.
  • Databases written before this change need wp reindex (schema unchanged, content rewritten); the log remains the source (§7.2), so reindexing is safe and repeatable.
  • searchable_text is deliberately shallow: it indexes what a record writes, not what a renderer derives. Known limitation (AEP-002, now with reproduced evidence): FTS5 unicode61 does not segment Chinese, so a multi-character query inside a longer Han run does not match — while guard-engine's own bigram tokenizer (crates/guard-engine/src/text.rs) would have. Retrieval is currently the weaker CJK matcher of the two.

ADR-019 — `.projectpack` is a stored zip whose manifest says "projection, not a second source of truth"

Statusaccepted
Date2026-10-03
RefV1_DEVELOPMENT §55; PROJECT_MASTER §19 禁止 4; ADR-002, ADR-011

Context

§55 requires six exports (timeline, project state, charter, decisions, AEPs, project map) and allows V1 to package them as .projectpack built from zip + json + md. The risk the master names repeatedly (禁止 4: 禁止维护两套 Project State) is a second materialized copy that drifts from the log. The packaging has to make its subordination legible to whoever unzips it months later.

Decision

wp export pack [FILE] (default project.projectpack, apps/cli/src/export.rs) writes a zip containing:

member content
manifest.json format / version / projectId / projectName / stateHash / members + the note
project-state.json the reducer's read-only projection
project-map.md the compiled map, byte-identical to wp export map
charter.json charter + scope + architecture baseline
decisions.json, aep.json state sections
timeline.json the accepted event log in seq order
  • Everything is read through project_read_only and the same compiler the workbench uses: exporting never advances a baseline, never appends an event, never saves a snapshot.
  • Compression is Stored, not Deflated: every member is JSON or markdown, and a reader without a zip codec should still be able to open the file. Size is not the point; legibility is.
  • manifest.stateHash is the map's source_state_hash, so a pack states which state it projects; the manifest carries the literal sentence "projection of the accepted log, not a second source of truth". apps/cli/tests/cli_e2e.rs asserts that sentence, and that the packed map equals the standalone wp export map byte for byte.

Consequences

  • timeline.json is a mandatory member, not an option: a pack without the log could not be replayed, and an unreplayable summary is exactly the second-source failure 禁止 4 warns about.
  • No import side exists in V1. An import would be a write path outside the event store (禁止 7/禁止 4 again); a pack is for moving knowledge to a human or another agent, not back in. Re-entering agent results is wp import / wp event, which go through the store.
  • Secret values are never members; only refs appear, and §53's policy filter runs before any adjacent context compile, so a pack is safe to hand to a cloud target for the same reason a context pack is.

ADR-021 — An adapter's health has exactly four outcomes, and the last run replaces the one before

Statusaccepted
Date2026-10-05
RefV1_DEVELOPMENT §51, §58, §62 Degradation; PROJECT_MASTER §7.9, §13.2 Stage H

Context

Stage H asks for "Adapter Health", §62 asks that degradation be reported rather than hidden, and §51 is the case that makes both necessary: a partial ingestion where material landed but the cursor did not move. The schema already had an adapter_states table (frozen in §49), but a table with no agreed vocabulary produces a status field that means whatever the last writer needed it to mean — and "error" written by five adapters is five different claims about whether an adapter works.

Silence is the failure mode here. An adapter that ingested nothing and said nothing is indistinguishable from one that is not installed, so the user cannot tell whether to fix something or to expect nothing.

Decision

  1. Four outcomes, each one something a pipeline run can actually observe (AdapterHealth, crates/domain/src/agent.rs): - ok — detected, ingested, cursor advanced. - unavailable — detect() found no such source on this machine. Nothing was attempted, so nothing failed. - degraded — material landed but part of the run failed, in practice the cursor write. The next run will re-send what is already stored and L1/L2 dedup will absorb it (§51). - failed — the run produced nothing and the cursor stayed where it was. Unavailable ≠ Failed is the load-bearing distinction: it is what keeps §62's honesty from turning "this source is not here" into a bug report against an adapter that is fine.
  2. One row per adapter, keyed by adapter id alone (AdapterState { adapterId, health, detail, updatedAt }, crates/core/src/ports.rs AdapterRepository). Not per project: a source that is absent from this machine is absent for every project on it. record_state replaces the row, so wp adapters shows the current verdict and never a stack of history.
  3. History stays where it already lives. The verdict is a cache of "what the last run learned", not a log; the event log and the §54 audit table remain the record of what happened. Inventing a second append-only history in adapter_states would be 禁止 4.
  4. detail is shown as-is — the error text or an empty-batch note, never a stack trace.

Consequences

  • Every pipeline run ends with an answer, including the runs that do nothing (crates/ingestion/tests/health.rs: a_clean_run_leaves_an_ok_verdict, a_source_that_is_not_here_is_unavailable_not_failed, material_that_landed_with_a_broken_cursor_is_degraded, a_second_run_replaces_the_verdict_rather_than_stacking_history).
  • wp adapters [--json] is the surface for Stage H's acceptance item, and it is a read of the port rather than a re-derivation.
  • Adding a fifth outcome means adding a state the pipeline cannot observe; the enum is the place to argue about that, not the CLI's formatter.
  • The table has no project column, so a future per-source, per-project health view is a schema change plus an AEP, not a silent widening of adapter_id.

ADR-022 — Watch signals are events with a verb in the payload, and they produce no verdict

Statusaccepted, amended 2026-10-06（第五轮的清点：deleted 从来不是 FILE_CHANGED 的 payload（删除走 ARTIFACT_DELETED）、FileScan::diff 其实是 FileScan::run、而"不改任何状态"只对 git 那两个信号成立——文件信号确实 upsert / mark artifact 行，所以这一条改成"不产生结论"，标题同批改掉）
Date2026-10-05
RefV1_DEVELOPMENT §16, §39, §19; PROJECT_MASTER §7.2, §7.3, 禁止 9

Context

§39 asks for the working copy to be watched: which branch, what is uncommitted, which files appeared, changed or vanished. §16's catalogue lists FILE_CHANGED and GIT_COMMIT and says "at least", and two of the signals §39 names — branch and dirty status — had no type at all.

Three questions had to be answered before writing anything, and each has a documented answer because the wrong one quietly breaks the project's core claim:

  • Does "the tree got dirty" belong in GIT_COMMIT? No: GIT_COMMIT means a commit exists. Folding a branch switch or a dirty tree into it would put facts in the log that history does not contain.
  • Does a file change belong in Project State? No: §19 makes completion a confirmed event, and 禁止 9 forbids treating an observation as the project's memory.
  • Does V1 need a watcher process? No: 禁止 8. A daemon would need a lifecycle, a config file and a failure mode that nothing in §13.2 accepts yet.

Decision

  1. Two new catalogue types for the git side, because they are different facts: GIT_BRANCH_CHANGED and GIT_STATUS_CHANGED (crates/domain/src/event_catalog.rs, listed in ALL so an unknown-type append still refuses them if they are ever removed).
  2. One type for the file side, FILE_CHANGED, with the verb in the payload: payload.change ∈ {created, modified, baseline} (ScanKind, crates/ingestion/src/file_scan.rs). The signal §39 wants is "this path changed, and here is how", and §16's list is a floor rather than a ceiling. One type keeps the dedup key honest — the payload is part of the event's identity, so the same path re-reported with the same hash appends nothing while a genuinely new hash does. baseline exists because the first pass over a directory is not a claim that anything changed; it is a snapshot the next pass can diff against. Amended 2026-10-06: this list used to include deleted, and it never emitted it. ScanKind does name deleted — a scan report has to say which paths vanished — but a removal leaves the log as ARTIFACT_DELETED (item 5), not as a FILE_CHANGED claiming a content change to bytes that are gone. The round-5 test a_vanished_file_leaves_a_removal_signal_and_no_new_verdict asserts both halves: one removal signal, and no FILE_CHANGED whose change reads deleted.
  3. Watching is a pass, not a process. GitFacts::watch_workspace reads branch and status now, compares them against the snapshot the previous pass left in settings, and appends only what differs. FileScan::run does the same against recorded hashes and returns a FileScanReport the caller can ask which paths were created, modified, deleted, or quiet. No thread, no timer, no filesystem notification API — so the same code runs behind a wp watch call and behind any future UI button, and nothing needs to be stopped or upgraded.
  4. They produce no verdict. Amended 2026-10-06 — this item used to say "the reducer changes no state for any of these", which is only true of half of them. What is actually guaranteed, and what the round-5 tests pin:
    • GIT_BRANCH_CHANGED / GIT_STATUS_CHANGED join TEST_* / BUILD_* in the projector's truly unfolded group (crates/state-engine/src/projector.rs) — they become Git-typed evidence rows and nothing else, which is why watch_signals_fold_into_no_project_state_at_all can assert an identical state hash.
    • The file signals do fold: FILE_CHANGED upserts an artifact row and ARTIFACT_DELETED marks it. Artifacts are part of state_hash_of, so a scan that finds a file changes the hash — and that is the right answer, because an artifact row is a statement about a file, which is exactly what the scan observed, not a statement about whether the project's work is done.
    • What no watch signal may touch is the judgement: a_vanished_file_leaves_a_removal_signal_and_no_new_verdict asserts the task, issue, decision, proposal and drift collections are untouched after a removal — 禁止 9 in a single test name. A dirty tree says where the work is.
  5. A vanished file gets ARTIFACT_DELETED, not a silent row edit — the artifact's history has to stay readable in the log, which is the only place §45 can point at.

ADR-023 — A backup is an online copy, made and restored through SQLite's own backup API

Statusaccepted
Date2026-10-05
RefV1_DEVELOPMENT §55 Export/Backup, §62 Recovery; PROJECT_MASTER §7.5, §13.2 Stage H; ADR-019

Context

Round 1 shipped §55's export side, so a project could already leave the machine as six documents or one .projectpack. That is not a backup: a pack is one project's projection, compiled at a moment, and it carries none of the workbench's settings, audit rows, indexes or other projects. Stage H and §62 Recovery ask for the whole database to be copyable, verifiable and restorable, and round 1's own KNOWN ISSUES recorded that gap ("导出已经能当备份用，但没有 restore 路径").

Two naive implementations are wrong in ways that only appear under real use:

  • std::fs::copy of the main .db file freezes whatever the WAL has not yet checkpointed, so a backup taken seconds after a write can silently lack it;
  • restoring by swapping files replaces a database this very process still holds open, which works on a laptop until it does not.

A backup you cannot verify is not a backup, and a restore that cannot be refused is a way to lose work.

Decision

  1. SQLite's Online Backup API in both directions (crates/storage/src/backup.rs, rusqlite's backup::Backup, 128 pages per step). Copy and restore go through the same mechanism the engine uses to keep a WAL database consistent, so "the copy matches a committed state" is the engine's claim rather than this crate's hope.
  2. PRAGMA integrity_check is the verdict, returned as SQLite's own string — "ok" or its first complaint — inside BackupReport together with schema version and row counts. The workbench never grades its own homework here.
  3. Maintenance is a separate port, not a twelfth repository. DatabaseMaintenance (backup_to / integrity_check / inspect / restore / schema_version) lives beside Repositories in crates/core/src/ports.rs and App holds it as its own handle, because no project logic reads the database as a file (§7.5). Paths are the only storage concept allowed to cross it.
  4. restorable(known_version) gates every read path: a file whose schema is newer than this build is refused before anything is copied, so a downgrade cannot half-succeed.
  5. Restore is destructive, and says so four times (apps/cli/src/backup.rs): - create refuses to copy a live database that is not whole; - restore stops without --yes, having explained what will be discarded; - restoring the live file onto itself is refused, because it would prove nothing; - the current database is snapshotted first — and if that fails, the failure is only warned, because Recovery must not be blocked by the safety net.
  6. Secrets are out of scope on purpose. Values never entered SQLite (ADR-017), so a backup carries secret_ref strings and a restore moves no credential. The report says so.

Consequences

  • wp backup create|status|verify|restore covers §55's backup side and §62's Recovery verb; a_backup_returns_the_workbench_to_an_earlier_moment (CLI) and six storage tests cover it, including restoring_discards_what_was_recorded_after_the_backup, an_unrelated_sqlite_file_is_refused_as_a_backup and a_missing_backup_is_not_found_rather_than_corrupt.
  • a_backup_reads_data_the_live_database_wrote_after_it_was_taken_nothing pins the property that matters most: the copy is a point-in-time snapshot, not a live view.
  • A pack and a backup remain different artifacts for different jobs; neither is a substitute, and the CLI's prose says which one it wrote.
  • Backup files are plain SQLite databases, so wp backup verify <file> works on a file from another machine — while sqlite3 file .dump also works, which is the escape hatch §62's "report the degradation" clause wants to exist.

ADR-024 — Level-3 near-duplicates are lexical hints, and a hint carries the thread it came from

Statusaccepted
Date2026-10-05
RefV1_DEVELOPMENT §52, §59, §60; PROJECT_MASTER §7.2, §19 禁止 9; AEP-002

Context

§52 splits deduplication into three levels and gives them two different powers. L1 (external id) and L2 (content hash plus role) are decided at insert and drop material, because "the same bytes again" is a fact a hash can prove. L3 is the soft case — two turns that say almost the same thing — and §52's rule for it is one clause: 只提示，不直接删除.

Round 1 shipped L1/L2 and left L3 with neither an implementation nor a surface, so "the same question twice this afternoon" was invisible. The tempting implementations were the two the spec forbids: merge the pair into one record, or write a hint into the event log as if it were a fact. The first destroys the trace §17 exists to keep; the second makes a guess a second state source (禁止 4).

A second problem is cheaper to hit and worse: the scan needs a window of recent messages, and the port that returns them ordered by observed_at alone. Same database, different answer.

Decision

  1. Lexical, not semantic (crates/ingestion/src/near_duplicate.rs): Jaccard over token sets, default threshold 0.8 — eight of ten distinct words agreeing. Semantic near-duplication needs an embedding or a model, which §60 prices as a Strong Model call and 禁止 7 keeps out of the core path; the vector version stays AEP-002's job.

  3.   4. Bounded by construction: a 240-message window, a limit on pairs, results sorted most-similar first, excerpts clipped on character boundaries so a truncated Chinese line stays readable.
  5. Cost is pruned before it is paid. Pairs grow as the square of the window, so similarity_upper_bound rejects a pair from set sizes alone when no score could reach the threshold — and the test proves the bound never rejects a pair the real score would accept.
  6. The window's order became deterministic: recent_messages now reads ORDER BY observed_at DESC, rowid DESC (crates/storage/src/conversation.rs) before reversing. rowid is store-assigned and monotonic, so it is the tie-break the timestamp cannot provide.

  • wp duplicates [--conversation <id>] [--threshold] [--window] [--limit] is a read-only command; there is no path from this module to a write, and crates/ingestion/tests/near_duplicate.rs asserts exactly that (the_pass_holds_no_way_to_write).
  • The CLI's e2e test closes the loop the way §52 wants it closed: import, take the hint, import the same file again, and show that nothing was deleted — the second import reports the rows as duplicates rather than fewer messages.
  • Fixing the tie-break changed a documented property ("oldest first"), so it is stated here: a projection whose inputs depend on index walk order is not deterministic, and §7.2's replay promise is what that would have broken — the hint surface just happened to be the first thing to read the window.
  • Re-running the same scan is stable (the test asserts byte-identical JSON twice), which is what lets a UI show hints without flicker later.
  • AEP-002's trigger is unchanged. What is new is a lexical stand-in whose number is visible, so a user who disagrees with a threshold can say so with evidence.

Date2026-10-05

Context

  • A payloadPath of None means "the text is only in the terminal" — an explicit statement rather than an absent field, so a UI cannot render a phantom file link.

  8. The event-log tool reads oldest-first. The store returns its newest window in seq DESC because that is what a LIMIT must cut from; the tool reverses it, so a model reading a history reads it in the order it happened and a limit still means "the most recent ones".

The other direction — the workbench pulling an agent's conversation in over MCP — is not shipped, and ADR-028 records it as owed rather than calling it out of scope.

ADR-030 — A creating event has to carry the whole record, because a fold rebuilds rows from the log alone

Statusaccepted, amended 2026-10-06 — the same cache bites §42.1's selection path too
Date2026-10-06
RefPROJECT_MASTER §7.2, §7.4, §19 禁止 4 / 禁止 6; V1_DEVELOPMENT §15–§18, §31, §33, §42.1; ADR-002, ADR-014, ADR-027, ADR-029

Context

The shell's first screen was built on diff_view, which folds through Reducer::project_state — the materializing fold. Ticking a change proposal and pressing 应用 reported success, and the scope baseline did not move. The cause was three links apart:

  1. open_change_proposal appended CHANGE_PROPOSAL_CREATED with a payload of proposalId and proposedChange only.
  2. Projector folds from an empty state (ADR-002), so the row it builds for that proposal holds exactly what that payload carried — reason: "", delta: None — and project_state persists those rebuilt rows.
  3. accept_change_proposal reads the row back from the store and, at the end, applies proposal.delta. With the delta lost, §7.4's "确认即锁定" skipped its own work in silence: the proposal was marked accepted and nothing was locked.

The guard-engine test for that same flow passed, because it accepted the in-memory proposal its own call had returned — before any fold had rebuilt the row. A test that never materializes cannot see this, and neither can a test that materializes but compares only counts and titles.

Decision

  1. CHANGE_PROPOSAL_CREATED's payload is the record: proposalId, proposedChange, reason, affectedScope, affectedArchitecture, benefit, cost, risk, charterConflict and delta. The event is where the record comes from, so it has to say what the record says.
  2. The general rule, stated for the kinds not yet written: every field a record must still show after a fold belongs in the event that created it. "The payload is enough for the projector to touch the field it switches on" is not the bar — the projector writes the whole row, so a field the log omits is a field the cache loses. 禁止 4 makes the projection disposable and the cache a rebuild; that is what makes log completeness the only thing that can keep a field alive.
  3. The regression test lives in the fold's own suite, not the UI's: a_proposal_survives_materialization_with_the_delta_it_was_opened_with (crates/state-engine/tests/reducer.rs) opens a proposal carrying a delta, folds with project_state, reads the row back and asserts reason, delta and status == Open. It fails against the previous payload, and it fails identically whether or not a window is compiled.
  4. Transition events keep a thin payload. CHANGE_PROPOSAL_ACCEPTED / _REJECTED carry proposalId, proposedChange, status and the human's reason — they are a change of mind about a record, and the projector reads only the status from them. Fixing this at the creating event, and not by fattening every payload in the catalog, keeps §18's "the log is the input" true without turning each transition into a full snapshot of the row.
  5. No backfill and no row patching. A log written before this decision keeps rebuilding the thin row it can rebuild; the remedy is to open the proposal again. Editing an entities row from outside the event chain would install 禁止 4's second source of truth, and that mistake costs more than the one this ADR fixes. V1 is a single-user local workbench, so no orphaned proposal is worth a migration.

Consequences

  • Creating payloads get bigger. That is storage bytes, paid deliberately: the cache must stay throwaway, so the log must stay complete.
  • project_read_only is now a documented hazard when used as a stand-in for materialization — it never writes rows, so a test built on it will pass while project_state is destroying data. Any assertion about cached rows must use the materializing fold.
  • The same cache bites a second time, in the other direction. §42.1 resolves a user's selection through repos.entities — the very rows the fold writes — so compiling a pack over a record that was accepted after the last wp map answered “not found in this project”. The fix is not a second read path: wp context dispatch, wp-mcp's context_pack and the shell's context_view each call project_state first, which is the write-through the map compile and a snapshot already performed. A fold-complete log plus an explicit materialize is the whole design; what was missing was saying which reads depend on it.
  • Field-level fidelity is per entity kind, and only ChangeProposal is proven here. The existing budget test compares folded and cached rows by count and title, which is a real but narrower guarantee; a new kind whose row shows more than its title inherits this question and answers it with one fold plus one row read.
  • The front end keeps no local copy of a proposal to fall back on. It renders what the fold produced, which is what surfaced this at the surface instead of leaving it in a database nobody reads (ADR-029).

ADR-031 — The browser's door is a push channel of four verbs, and open / inject are answered as instructions, not acts

Statusaccepted, amended 2026-10-06 — §35 的 origin 检查有两副面孔
Date2026-10-06
RefV1_DEVELOPMENT §34, §35, §36, §37, §38, §51, §53, §58, §60, §62; PROJECT_MASTER §7.1 V1-D, §14, 禁止 7, 禁止 8, 禁止 10; ADR-020, ADR-025, ADR-027, ADR-028, ADR-030

Context

V1-D 记了三轮 “◐”，缺的从来不是读文件的那一半 —— Manual Import、transcript、CLI session 都有适配器了。缺的是 §34 与 §35 那一行：活的网页会话如何进入工作台，以及工作台编译好的 Context Pack 如何回到网页。§38.5 的 MCP 那扇门（ADR-026、ADR-028）读得出去，读不进来，所以它替不了这条链路。

把这条链路落下来时有六个问题不能含糊，每一个都决定了 Core 的形状：

  1. Native Messaging 的宿主是一个被启动的进程，Chrome 只给它 stdin 与 stdout，不给参数，也不给第二个通道 —— 那 --project 这类作用域写在哪里？
  2. §34 要求扩展 打开目标网页 与 准备输入内容。宿主在浏览器里没有手，只有回话的嘴 —— 一个答不出的动词该不该留在契约里？
  3. §35 列了五项必须验证的东西，但没说失败长什么样；§62 Degradation 又要求失败必须可回答。
  4. 浏览器推来的一批消息，是该写成第八个 AgentAdapter，还是走别的路？
  5. 一个 CLI 进程（wp context prepare）退出之后，它编译的包怎么还能“注入”？
  6. 扩展能不能信？origin 字段是谁在担保？

Decision

  1. 一个版本串，四个动词，一问一答，永不监听。 codlas-nm/1： hello（握手并报能力）、capture（导入新消息）、open（打开目标页）、 inject（把包放进输入框）。没有端口、没有 socket、没有后台守护 —— 通道的生命周期就是 Chrome 给的那个 stdio。 帧是四个小端字节的长度前缀加 UTF-8 JSON，长度超过 1 MiB 的帧在解析任何 JSON 之前就被拒掉，这是 §35 的 size 检查唯一说得通的位置。
  2. open 与 inject 答的是指令，不是动作。 宿主回 {action:"openTab",url} 与 {action:"fillComposer",text,send:false}，由 service worker 去执行。这不只是能力限制，它同时是 §37 与 §7.8 的形状： send:false 是协议里一个写死的字段，而不是一个可以商量的默认值 —— 工作台永远不递交。 inject 的回复里带一句原文 “the workbench fills the composer; sending stays your action”， 和 §62 Degradation 那句 fallback 同源，用户在一个地方看到的解释与在另一个地方看到的解释不是两份。
  3. §35 的五项检查各自拥有一个拒绝前缀：origin rejected / command rejected / payload rejected / size rejected / project scope rejected，且一条坏帧只结束那一帧： 会话继续（§62 的“静默”才是失败，报出来的不是）。测试按前缀断言，因此一个检查失效不会被另一个的失败掩盖。
  4. 浏览器推来的材料走 IngestPipeline::ingest_messages，不是新适配器。 一个线程 = 一个 Source（§51 的游标粒度就是按 source 划的，这条本来就写在 adapter.rs 的模块说明里）， payload.source 只能是 chatgpt_web 或 generic_web，身份与去重仍由 pipeline 决定。 适配器是读者：它没有可以主动去读的地方 —— 活的会话在浏览器一侧，是被推的一方 —— 所以给它造一个第八个 trait 只会把 “谁来发起”这件事说假。ingest_messages 的文档注释里那句 “a browser push, a test fixture” 等的就是这条链路。
  5. AgentAdapter::inject() 在 V1 仍然对所有已交付适配器返回 Ok(None)，而这一次是结论不是缺口。 CLI 进程退出后不留通道：要让它“注入”，就得先有一个常驻进程和一个作用域未定的连接，那是 §37 的 AUTO_EXECUTE 与 禁止 10 的门口。真正的输送在宿主这一侧完成，而调用它的人是扩展弹窗里按下按钮的人。 ADR-028 欠的那一半（入站采集）仍然挂账，本决定不替它抵账。
  6. 信任锚是 manifest 的 allowed_origins，origin 字段只是自述：只有 manifest 列出的扩展 id 能连上宿主， 这是 Chrome 给的；请求里的 origin 是扩展报告这批内容来自哪个页面，宿主仍按 §35 校验它（不在白名单就拒）， 但文档写清它是一致性门而非安全边界。同一个白名单同时管 open 的目标 URL，所以一个编译好的包 无法把人带向 chatgpt.com.evil.test 这类形似域名。§53 与这条无关：密钥从来不走这条路。
    就地修订（同一轮，宿主与扩展对接时）：这条检查有两副面孔，因为四个动词里有两个字面意义上没有页面可报。 capture（读哪个页面）与 inject（往哪个页面打字）必须报白名单里的 https://<host>； hello（自检）与 open（把某页带到前台）不经手任何页面材料，可以报扩展自己的 chrome-extension://<id> —— 那枚 id 正是 Chrome 在 allowed_origins 上已经核过的东西， 所以这不是让宿主相信一句新的自述。open 的目标 URL 仍走它自己的白名单，两件事没有互相顶替。 测试是 the_popup_names_itself_on_hello_and_open_and_a_page_on_the_page_commands：同一枚扩展 origin 送到 capture 与 inject 必须拿到 origin rejected，而带路径的 chrome-extension://id/settings.html 不是 origin。
  7. 宿主是 wp 的子命令，不是第十三个成员。 wp host serve 与 wp host manifest 落在 apps/cli/src/host.rs，workspace 仍是 12 份 manifest （ADR-027 的巡检没有为新成员改写）。manifest 命令写的是两个文件：Chrome 那个记录， 和记录所指向的 wrapper 脚本 —— 因为 Chrome 不传参数，作用域只能烘焙在脚本里；路径逐单引号转义， 带空格的路径在 macOS 上是常态。

Consequences

  • serve 期间的 stdout 属于协议。 这是全 CLI 唯一一处人类可读输出必须走 stderr 的命令， 写在这个模块的头部注释里；host manifest 仍然是正常打印，因为它是被人在终端里敲的。
  • 浏览器开着的时候会有第二个 SQLite 连接。一次 capture 是一个短事务，扩展没有任何本地状态（§34 的“不负责”清单）， 所以标签页丢了不丢工作bench 的东西。
  • §58 的 E2E 那一行（Browser → Extension → Native → Event → State → Project Map → Select Issue → Context Pack → Browser Prepare）第一次真的跑通了：测试用自己重写的一份编解码驱动真二进制，不复用 crate 的 codec —— 共享 helper 会替宿主隐瞒它自己发出去的字节，手写的那份不会。
  • 同一轮里 §53 在浏览器路径上被看见了一次：这个 fixture 项目 allowCloudModel=false，所以 --to chatgpt 的包被整包拒绝，链路上走的是“不声明去处”的包。这不是绕行： §53 管的正是“去处”，而把包搬进浏览器的人是 §7.8 里那个动手的人。
  • V1-D 仍然是 ◐，但缺的东西换了：采集这条链路（§34/§35/§38.2/§38.3 的活会话一半）已经落地， 还欠的是 ADR-028 的入站 MCP 采集。写回总控时按这一条写，不写成“做完了”。
  • 扩展与宿主之间是约定不是类型检查：JS 那边改了字段名，Rust 这边只会以 payload rejected 回答。 因此 apps/extension/README.md 里那份协议表和这个模块必须同轮改动，这是本决定唯一的额外维护费。

ADR-032 — A compiled Context Pack is audited, not stored: §50's context_packs table does not exist

Statusaccepted (2026-10-06, fifth round: the V1 completeness audit found the only §50 table name with no counterpart)
Date2026-10-06
RefV1_DEVELOPMENT §41, §42, §43, §49, §50, §54; PROJECT_MASTER §19 禁止 4, §14; ADR-002, ADR-011, ADR-013, ADR-019

Context

§49 lists context_packs and context_pack_items; §50 shrinks the list to a minimum database and keeps context_packs in it. The V1 completeness audit walked §50 line by line against CREATE TABLE statements in crates/storage/src/schema.rs and its migrations: every name in that minimum list has a table except context_packs. It is not collapsed into the entities table the way ADR-013 collapsed the record kinds — the rows were never written, because nothing reads them.

What the pack is made of is already durable, somewhere else. Every successful compile writes exactly one audit_logs row (§54, crates/context-engine/src/compiler.rs): produced_ref is context_pack:<id>, read_refs are the records the pack cited, redacted_refs the §53 hits, plus the target agent, the weighting and the trimmed/kept outcome. That is the row a context_packs table would hold, and the item list a context_pack_items table would hold is the read_refs array. wp audit is the reader.

Decision

  1. V1 keeps no pack table. A pack is a pure function of (the state at compile time, the request, the budget, the policy) — §41's own definition of it as compiled output. Storing its items as rows creates a second copy of project facts that can outlive the records it was compiled from, which is 禁止 4 in its most literal form: the pack would say "issue I-1 is open" after I-1 was resolved, and the log would say otherwise, and nothing would reconcile them.
  2. Traceability is satisfied by the audit row plus determinism. The audit row says which pack existed, what it read, what was redacted and where it was sent; re-running the same request recompiles the same bytes (compiling_twice_over_the_same_log_yields_the_same_bytes), so "what did the agent get" is answerable without a copy of the answer. §62's Traceability gate is met by that pair, not by a table.
  3. The §41 pack is still a file when a human wants it. wp context build --out writes the markdown and ADR-019's .projectpack carries the state it was compiled from, both declaring themselves projections. Those are the two supported ways a pack leaves the process; neither is a database row.
  4. Trigger to revisit, written down so it is not rediscovered. Build durable pack storage when a requirement asks to reproduce byte-for-byte what an agent was handed at a past moment after the underlying records have been amended — a replay-after-correction requirement, which V1 states nowhere. The honest shape at that point is a content-addressed artifact in the existing evidence table (the same subordination argument as ADR-019's zip), not a normalized context_pack_items.

Consequences

  • §50's minimum list is now met by name except for context_packs, and this record is the reason. A future audit that greps table names against §50 should read this entry before treating the miss as a defect.
  • Nothing to migrate or back up beyond audit_logs, which §55 already exports — so the audit's "packs are invisible" concern is inverted: the pack index is the part that survives a restore.
  • A pack's full text is not re-readable after the process exits. The audit row records that it was compiled and what it read; recovering the exact prose means recompiling. If that ever stops being acceptable, it is the trigger in item 4 firing, and this is the entry to amend.

ADR-033 — §52's L2 key is content hash per role: a dedup level must not delete evidence

Statusaccepted (2026-10-06, fifth round: found by walking §52 against the INSERT statement, not by a failing test)
Date2026-10-06
RefV1_DEVELOPMENT §52, §51, §49, §14 第 3 项; PROJECT_MASTER §19 禁止 9, §7.1 V1-D; ADR-013, ADR-014, ADR-024

Context

§52 gives three levels: L1 External ID, L2 "Content Hash + Role + Time Window", L3 semantic near-duplicate, and it says out loud that L3 only hints and never deletes. The first cut implemented L2 as ON CONFLICT(conversation_id, content_hash) DO NOTHING — the role was in the row but not in the key, and the time window was nowhere. Two consequences, both visible in a real conversation:

  • the user types "继续" and the assistant also says "继续" — the second one is never stored, because the pair (conversation, hash) already existed;
  • the same short phrase genuinely said twice, an hour apart — the second occurrence disappears.

A round-1 test pinned the behaviour as it was implemented (full_text_matches_a_whole_token_not_a_piece_of_a_chinese_run era, ADR-018) so nothing looked wrong: re-pushing a transcript stayed idempotent, which is what §51 asks for. What was being sacrificed is what 禁止 9 protects from the other direction — captured material is evidence, and an ingestion layer that silently drops turns is a smaller version of the same "chat history is editable memory" failure. The dedup level exists to stop double counting, not to stop storing.

Decision

  1. The role joins the identity key. L2 is now (conversation_id, role, content_hash), created as idx_messages_l2 by migration v4 (messages_dedup_key_includes_role) in crates/storage/src/schema.rs. Same text, different role = two turns, both real.
  2. The time window deliberately does not join it, and that is a reading of §52 rather than an omission of it. §51 requires re-ingestion to be idempotent; a message's timestamp can be absent (manual paste) or jittery (a snapshot export re-emitted later). A time component inside a UNIQUE key therefore makes the property that matters most — "pushing the same file twice adds nothing" — depend on data that is optional. "Same text, same role, said again later" is exactly what L3 exists for: wp duplicates reports it as a hint and touches no row (ADR-024).
  3. The table is rebuilt, not altered. The baseline declared the uniqueness as an inline UNIQUE(conversation_id, content_hash) constraint, and SQLite will not drop the automatic index behind one — so v4 creates messages_v4, copies, drops, renames and recreates the three indexes, which is the same shape ADR-013's migration v3 used for entities. Forward migration, not an edit to v1: a user's existing database has to upgrade rather than be discarded (§49's purpose).

Consequences

  • One row per (conversation, role, text) is still guaranteed, so the idempotency assertions ADR-014 and §51 rely on are unchanged — re-running an adapter adds no message and no event (re_running_an_adapter_yields_no_duplicates_and_one_cursor_move still passes).
  • A repeated identical turn inside one conversation is now stored and reported by L3 as a near-duplicate hint. Counting changes: a transcript where the user says "继续" five times yields five messages rather than one. That is the honest record of what happened.
  • §52's "Time Window" is now a documented, reasoned non-implementation rather than a silent gap. If a future requirement needs it, it belongs to L3's window parameter, not to the identity key.
  • ADR-013 quoted the old key as the example of a constraint worth its own table; that sentence is amended to point here.

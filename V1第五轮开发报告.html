一、本轮范围：问题不是"下一步做什么"

前四轮的记录都是当轮自报：写了什么、测到什么、账上就记什么。本轮把输入换成一个问题—— 有没有哪一行是拿"应该做了"当证据记上去的？核对对象是三份文档里所有可核的清单： PROJECT_MASTER.md §21 的八段五十四项、V1_DEVELOPMENT.md §14 的十条验收、 §62 的七道发布门。核对方式只有一种：回到代码与测试文件，不读上一轮的报告，也不读 §20 的自述。

结果分三类，处理方式也各不相同：

类别判据本轮处理
真缺文档要求一个行为，代码里没有任何东西产生这个行为 补：§52 的 L2 键、§46/§47 的两屏内容
已做，但没有测试声称过代码路径完整，任何测试名里都找不到它 补测试：milestone、§28 阶梯、§14 第 10 项、§39 的删除信号
账写过头文档的措辞比代码能保证的强 改账：ADR-013 / ADR-016 / ADR-020 / ADR-022 就地修订
为什么"已做但没被声称"要单独算一类：这一类不会让任何测试变红。 它的意思是——下一个人改坏这条路径时，没有一个人会被告知。本轮查出的四处里有两处属于这里。

ADR-013 / 016 / 020 / 022

§52 的 L2 键少了 role：一个会吃掉证据的去重层

基线键是 (conversation_id, content_hash)。于是：

  • 用户说"继续"、助手也答"继续"——第二条被静默丢弃；
  • 同一句话一小时后说第二遍——同样被丢弃；
  • 而第一轮有一条测试 duplicate_messages_are_dropped_on_reingest 把这个行为钉成了需求。

去重层的职责是阻止同一份材料被重复计数，它没有权力删内容：捕获来的材料是证据（§17、§7.3）。 修法与代价见 ADR-033； 时间窗仍然不进键——§51 要求重推幂等，而来源时间戳可能缺失或抖动， "同一句话后来又说了一遍"归 L3 提示，提示永不删除（ADR-024）。 SQLite 不肯 drop 内联 UNIQUE 背后的自动索引，所以与 ADR-013 的 v3 同一副骨架：migration v4 重建表 （messages_dedup_key_includes_role），而不是 ALTER。

§50 的 context_packs 表不存在——这是决定，不是漏建

§50 的库最小清单里点名的表，逐张对上了 crates/storage/src/schema.rs，只有 context_packs 没有。 包是按需编译的：编译一次留一行 audit_logs（produced_ref = context_pack:<id>、 read_refs、redacted_refs、目标 agent），成品以文件出去（wp context build --out、.projectpack）。 再存一张表等于把项目事实抄第二份（§19 禁止 4）。重看的触发条件与届时的形状写在 ADR-032。

五、改掉的账：三处写过头

条目原来的说法代码里的事实
ADR-022 payload.change ∈ {created, modified, deleted, baseline}；引用 FileScan::diff； "这些事件一律不折叠，不动任何状态" 删除从来不走 FILE_CHANGED，它发 ARTIFACT_DELETED；那个方法叫 FileScan::run； 而"不折叠"只对 GIT_BRANCH_CHANGED / GIT_STATUS_CHANGED 成立——文件信号确实 upsert / mark artifact 行，而 artifacts 在 state_hash_of 里。 标题因此由"move no state"改为"produce no verdict"：不许触碰的是结论， 不是文件行——禁止 9 的真意就在这里
ADR-013 引用 §52 的 L2 键作为约束 键已经变宽（随 ADR-033），约束句同轮改写并指向 migration v4
ADR-016 §14 十条"在第一轮以核心 + CLI 层级跑通"；§29 的七种 Inbox 不置一词 第 10 项此前只有反面证明；本轮它有了自己的测试。§29 的 merge candidate 与 unverified claim 按设计没有持久生产者，这一条现在写进了 Deferred 清单而不是留成沉默
ADR-020 测试层四层、cli_e2e 20 条、views.rs 12 条 新增 crates/ingestion/tests/resolution.rs 一层解析阶梯测试； e2e 与视图层条数随本轮上升（见下表）

另有一处非文档的账：crates/core/src/ports.rs 的 insert_messages 契约注释还在说 "content hash within the conversation"。端口注释也是契约——它比实现慢一拍就会误导下一个实现者，同轮改为 "content hash per role"，并写明键里为什么没有时间戳。

六、§46 与 §47：从"有命令"到"有屏幕"

上一轮的账写的是"§21 列的八个屏幕全部有对应命令与视图构造器"。这句话是真的，但它遮住了一个事实： 那两个构造器返回的是空壳。有命令不等于有屏幕——这是本轮方法上最值得留下的一条。

§46 总览必答现在从哪来答不出时
最初目标是什么Charter 的 originalProblem / coreValue（版本化、用户锁定） 写进 gaps，由屏幕自己说出来（ADR-011 的空 section 自己声明为空）
当前阶段是什么project.currentPhase
最近发生了什么最近三条已接受事件，取自时间线构造器本身（不另写一套排序）
当前最大问题是什么打开的 Issue，按折叠顺序——计数不重排
有没有偏航guard-engine 的六条词法规则命中数
下一步是什么直接取编译好的 PROJECT_MAP 的 Next Actions，不在屏幕里再推一次
§47 演进屏五项处理方式
Architecture Baseline取物化状态里的 baseline（summary / layers / invariants / replaceableParts / version）
AEP Registrystate.aeps 全量，逐份带 §32 的全部字段
Triggered AEP按 AepStatus 分组：触发 / 进行中单列，让"该改了"从列表里站出来
Completed Evolution同上分组，完成的与休眠的各归一处；计数而非重排
Active ADR这一项指出去，不建表：ADR 是 docs/adr/ 里的文档， 屏幕为它新建一个持久生产者就是第二个状态来源（禁止 4，与 ADR-032 同一套理由）， 于是它出现在 gaps 里而不是列表里

两屏的 Rust 视图构造器与 ui/app.js 的渲染同时改：Rust 侧给字段，JS 侧把字段摆出来， 两边都过视图层测试——apps/desktop/tests/views.rs 不启动 webview 就能驱动整条读路径 （ADR-020 的 lib/bin 切开）。 webview 的像素仍是人工核对，这条限制与 ADR-029 给桌面壳留的那条是同一句，本轮没有把它说小。

十一、仍然没做（以及为什么不算偷工）

  • §38.5 的入站 MCP 采集——工作台主动去读 agent 那边的会话。 词汇表里 SourceType::Mcp 已在，wp import transcript --source-type mcp 也收文件， 但工作区没有任何代码向外开 MCP 连接。缺的不是代码位置，是一个真的、值得主动去读的会话源； 触发条件、McpClientAdapter 七个动词的映射、以及"必须 stdio 阻塞、不许为此引 async runtime" （§60 的 manifest 巡检说了算）全部记在 ADR-028。 §26 的 V1-D 因此仍是 ◐，不是 ✅。
  • 桌面壳的 webview 像素（ADR-029）与扩展在真 Chrome 里的表现（ADR-031）。 这两条是同一类残留：视图层测试能证明字段与逻辑，证明不了渲染。本轮没有把它们说成已完成， 也没有把它们升格成"缺口"——它们是人的下一步。
  • §29 的 merge candidate / unverified claim 没有持久生产者：本轮记下来而没有建表。 建表要 §16 没列的事件类型，且会造出第二个状态来源（禁止 4）；没有触发条件就先建，正是禁止 8。
  • §40 的 CJK 语义检索、AEP-001…005、crates/agent-runtime 与 packages/*：全部是未触发，按 §19 禁止 8 属于"不该做"，不是"没做完"。
关于"V1 是否全部完成"这句结论：现在能写的是——八段里除 V1-D 的入站采集之外， §21 的五十四个条目没有一个留着未写的代码，§14 的十条与 §62 的七门逐条有测试名； 还不能写的是"V1 已完成"——那需要 ADR-028 的那半扇门，以及人在真浏览器与真窗口里各看一次。
